# Reject chain configs that skip a fork their rules depend on

## Context

`ChainConfig.CheckConfigForkOrder` (`params/config.go`) compared only pairs of forks that were both configured, so it caught a reordered pair but not a skipped fork: `{"chainId": 50, "osakaBlock": 0}` was accepted with every earlier standard fork unset. Every fork slot in this chain config carries `forkOrderOptional: true` (`params/config_backfill_fields.json`), so the `not enabled, but … enabled` branch that upstream go-ethereum added in `c476460cb2` (#20169) — which leans on the non-optional `shanghaiTime` — has no counterpart here. `git log -S"not enabled, but" -- .` finds nothing in this repository's history, including the three commits that introduced `alwaysOptionalChainConfigForkOrderField` (`dfce638a1a`, `e40eb38078`, `8f04a06e00`), so the branch was never ported rather than removed.

A skipped fork is not cosmetic, because the rule layer is selected by flags rather than derived from the highest configured fork: `activePrecompiledContracts` (`core/vm/contracts.go`) picks one whole precompile bag by the highest active flag, and the instruction-set switch (`core/vm/evm.go`) picks one whole jump table the same way. A config that enables Berlin and later forks while leaving Istanbul unset therefore runs its opcode tables on an Istanbul base while its precompile bag silently stays on the Byzantium set — missing `blake2f` and pricing bn256 at the Byzantium tier. Issue #2771 records the shape and its consequences.

## Decision

`CheckConfigForkOrder` gains a second, independent scan over the **standard** (Ethereum-derived) fork slots, in `forkOrder` order.

The **trigger set** is the 16 standard slots: Homestead, EIP150, EIP155, EIP158, Byzantium, Constantinople, Petersburg, Istanbul, Berlin, London, Merge, Shanghai, EIP1559, Cancun, Prague, Osaka. XDC-specific forks are not part of it: they are interleaved in `forkOrder` (24/25 sit between `shanghaiBlock` 23 and `eip1559Block` 26; 30–33 follow `osakaBlock` 29), so triggering on them would reject `TestnetChainConfig`, `DevnetChainConfig` and `LocalnetChainConfig`, whose trailing XDC forks are scheduled while Prague/Osaka are not. `daoForkBlock` (order 3) is deliberately excluded as well, matching upstream, where it is the one optional standard fork.

The **required set** is the subset of those slots whose flag production code still reads as `rules.Is<Fork>`, and whose reading is not the table-selection switch alone. Two shapes qualify. The first is a fork whose flag the precompile-bag switch in `core/vm/contracts.go` reads: those bags are not supersets of one another and its `default` arm is unconditional, so skipping one regresses the whole bag while the instruction table keeps advancing. The second is a fork whose own flag a cross-cutting rule reads directly — signer selection, intrinsic gas, the call-gas 63/64 rule, empty-account deletion. A read that only picks a layer of the instruction-set switch in `core/vm/evm.go` does not qualify, because no layer drops an opcode a lower layer defines — each step only adds opcodes or reprices the ones it keeps, and the Berlin step does neither, its table being identical to Istanbul's — and that is what keeps Berlin, London, Merge, Shanghai and Cancun in the trigger set only. Leaving a qualifying fork unset would put a rule this chain runs with into a bucket no schedule asked for: Homestead, EIP150, EIP155, EIP158, Byzantium, Petersburg, Istanbul, EIP1559, Prague, Osaka. Verified per member against non-test code on 2026-10-09 with `git grep -nE '\.Is[A-Za-z0-9]+[^A-Za-z0-9_]' -- '*.go' | grep -v _test`, key anchors: Homestead `core/types/transaction_signing.go:50`, `core/state_transition.go:408`; EIP150 `core/vm/gas_table.go:403`; EIP155 `core/types/transaction_signing.go:48`; EIP158 `core/blockchain.go:2205`; Byzantium `core/vm/contracts.go:235`; Petersburg `core/vm/gas_table.go:109`; Istanbul `core/vm/contracts.go:233`, `core/vm/evm.go:164`; EIP1559 `core/vm/contracts.go:229`, `core/vm/evm.go:538`; Prague `core/state_processor.go:102`; Osaka `core/vm/contracts.go:225`, `core/block_validator.go:60`. Every member is required unconditionally.

The remaining standard slots stay in the trigger set only. Constantinople's one relevant consumer tolerates its absence (`core/vm/gas_table.go:109` — `IsPetersburg || !IsConstantinople`, so an unset Constantinople correctly falls back to the legacy rule), and Berlin, London, Merge, Shanghai and Cancun do not have to be declared either. Their instruction-set layers are non-decreasing: every layer keeps the opcodes the layer below defines and only adds or reprices them, so no step is smaller than its predecessor. `newBerlinInstructionSet` is `newIstanbulInstructionSet` with `enable2929` commented out (`core/vm/jump_table.go:152`, introduced that way in `928a0691ca`), which makes that step identical rather than strictly larger — this repository carries the EIP-2929 repricing in the `eip1559Block` layer instead (`core/vm/jump_table.go:117`). The cascade is `newPrague ← newCancun ← newEip1559 ← newShanghai ← newMerge ← newLondon ← newBerlin ← newIstanbul ← newConstantinople ← newByzantium`. Skipping one of them only means missing what that layer adds or reprices — for Berlin, nothing at all — so no rule the chain runs with is left in an unasked-for bucket.

**Petersburg sits in the required set unconditionally.** Reading the SSTORE gate `IsPetersburg || !IsConstantinople` (`core/vm/gas_table.go:109`) alone would suggest the slot can be skipped on a chain that never declares `ConstantinopleBlock`, because the gate then takes the legacy branch either way; that reading is what this check deliberately does not follow. Upstream requires the slot for the same reason: `petersburgBlock` and `istanbulBlock` are both non-optional there (`params/config.go`), so a scheduled `istanbulBlock` with `petersburgBlock` unset is rejected by the existence branch, and geth #21473 states the intent verbatim — "fork ordering requirements which state that Petersburg fork be set if Constantinople fork is set" — while allowing Petersburg at the same block as Constantinople. Every slot here is optional, so the requirement is carried as a data-table flag (`forkSequenceRequired` in `params/config_backfill_fields.json`) rather than as a property of the slot's presence rule, and the one shape the sequence scan cannot see — a schedule that stops at `ConstantinopleBlock` — is covered by the pair check in the next paragraph.

That pair is also the one place where the check does not wait for a later fork to be scheduled. The sequence scan below reports a gap only when a slot that carries a value follows, so it cannot see a schedule that stops at `ConstantinopleBlock`; `chainConfigForkSequencePetersburgPair` (`params/config_backfill.go`) reports the pair on its own, and `CheckConfigForkOrder` rejects it with the same wording. Schedules that declare `PetersburgBlock`, or that activate it through `TIPXDCXCancellationFeeBlock`, stay valid, and so does Petersburg scheduled above Constantinople — upstream's `IsPetersburg` is false in that window too, so there is no divergence to close.

**Effective activation** is applied to required members only, and to the two that have a second activation path — Istanbul and Petersburg: `IstanbulBlock`, or `TIPXDCXCancellationFeeBlock` when the former is unset, mirroring `ChainConfig.IsIstanbul` (`params/config_forks.go:79-81`); and `PetersburgBlock`, or the same `TIPXDCXCancellationFeeBlock`, mirroring `ChainConfig.IsPetersburg` (`params/config_forks.go:66-68`). Both mirrorings are existence for existence. `TIPXDCXMinerDisableBlock` deliberately does **not** count. Its XDCv2 bag takes over only from `TIPXDCXMinerDisableBlock` until EIP1559 (`activePrecompiledContracts` tests `IsEIP1559` before `IsXDCxDisable`), so below `TIPXDCXMinerDisableBlock` the skipped Istanbul bag would still apply, and `IsXDCxDisable` plays no part in the instruction-set switch at all; a config that never activates Istanbul is not made consistent by scheduling the miner disable. Configs of that shape are rejected, and the error names the missing fork, which is the actionable fix.

The algorithm reports the nearest required predecessor, not the earliest gap: for every slot with a value, if the last required member seen was unset it fails. State starts as "nothing required seen yet", each slot is checked before the state is updated, and "last required" is strictly the previous required member. A naive variant that updates first and starts at "missing" still accepts all eleven built-in configs but silently stops rejecting `osaka only`, `eip1559 only` and `prague only`.

The scan runs inside `CheckConfigForkOrder`, after the existing linear comparison and before the `chainConfigForkOrderSpecialCaseRules` loop, so a real inversion (`EIP158Block 100` against an XDC fork at 50) keeps reporting the existing error. It returns `ErrWrongForkSwitchOrder` with the wording introduced for the Amsterdam rule in #2756: `invalid chain config: wrong fork switch order: %s is unset, but %s %v is scheduled`.

The check is **one-way**: only "a later standard fork is scheduled while a required earlier one is missing" is rejected. The mirrored shape — a complete prefix with later forks simply absent — stays valid by design, because a fork that is never scheduled is not a skipped fork. The Petersburg pair above is the sole exception and is not a gap in the one-way rule: it is rejected not because a later fork appears but because a declared fork alone decides which bucket its rule lands in. That is how a chain with a partially migrated schedule keeps starting; EIP1559 is the sharpest example, since a prefix that stops at London runs Berlin/London tables without the EIP-3860 semantics the EIP1559 flag carries here. Widening the check to that direction would reject built-in networks and is out of scope.

The sets are data-driven, not hand-written in the check: `params/config_backfill_fields.json` marks slots with `forkOrderStandard` and `forkSequenceRequired`, and the generator (`params/config_backfill_generator.go`) validates that both keys appear only on slots with a `forkOrder` and that `forkSequenceRequired` implies `forkOrderStandard`. The emitted table (`params/config_backfill_generated.go`) feeds `ForEachChainConfigForkSequenceBlock` (`params/config_backfill.go`), and `TestChainConfigForkSequenceRequiredSet` pins the required list, so a change to the set has to be a deliberate edit. The pair check that does not wait for a later fork lives in `chainConfigForkSequencePetersburgPair` and is pinned by `TestChainConfigForkSequencePetersburgPairInvariant`. The fallback rule is written twice, once for the runtime flags and once for the validation, and `TestChainConfigForkSequenceFallbackMirrorsRuntimeFlags` is what keeps the two copies in step.

## Consequences

### Migration note

A custom or legacy chain config that schedules a standard fork without declaring the required prefix, or that declares no standard forks at all while relying on a migrated `TIPXDCXCancellationFeeBlock`, now fails at startup. The built-in networks are unaffected, though their shape is worth stating precisely: XDCMainnet (50), Mainnet (1), Testnet (51), Devnet (551) and Localnet (5151) all leave `constantinopleBlock`, `petersburgBlock` and `istanbulBlock` unset (`params/config_networks.go:302-304`, `:363-365`, `:410-412`, `:472-474`, `:534-536`), and the first four rely on `TIPXDCXCancellationFeeBlock` (38383838, 23779191, 0, 0) as the effective Petersburg and Istanbul cutoff — the same fallback serving both, not Istanbul alone. `MainnetChainConfig` has no fallback either. `IsConstantinople` has no fallback and stays false on those networks, which is why Petersburg's unconditional requirement does not bite them: the four fallback networks keep the slot declared through `TIPXDCXCancellationFeeBlock`, and `MainnetChainConfig` schedules no later standard slot for the sequence scan to trip on.

An already-initialized chain with such a config does not keep running either, because a stored config is validated on every startup, not only a provided one: `SetupGenesisBlockWithOverride` resolves the stored config (with no `--genesis`, `chainConfigOrDefault` returns it) and `resolveSetupStoredConfigResult` calls `CheckConfigForkOrder` on it, `XDPoS.New` checks the same config again, and the read-only `LoadChainConfigWithCompatWithOverride` path rejects it as well. Upstream is the same shape — geth's own config-resolution helper ends in `cfg.CheckConfigForkOrder()`.

Correcting such a config is therefore not a detail but a rule change, and the honest options are to accept it as one or to stay on the previous release. Declaring `HomesteadBlock` changes the signer `MakeSigner` selects (Frontier versus Homestead) and the contract-creation intrinsic gas (21000 versus 53000), and declaring `EIP158Block` flips `deleteEmptyObjects`, which changes the state root every block was committed with; a node that re-executes older blocks under the corrected schedule computes a different root. That is the price of keying the check on the same predicate the runtime uses, `IsIstanbul` and `IsPetersburg` with their fallback included.

### Blast radius

Eight test fixtures were completed with the earlier standard forks so their subject (DAO fork ranges, the gas-tier rules, EIP-161 removal, worker pre-commit handling, the XDPoS V2 validation cases, `ExampleGenerateChain`) is unchanged: `cmd/XDC/dao_test.go`, `core/blockchain_test.go`, `core/chain_makers_test.go`, `core/genesis_compat_test.go` (two closures), `core/genesis_load_test.go`, `core/genesis_setup_test.go` (five configs), `core/state_processor_test.go`, `miner/worker_test.go` — thirteen fixture sites in all. Four of them exercise the migrated `TIPXDCXCancellationFeeBlock` path — the same path that keeps the built-in networks valid — which is why the effective-value rule is load-bearing rather than cosmetic. The unconditional Petersburg requirement added one more edit of the same kind: the `core/state_processor_test.go` config that schedules `istanbulBlock` from genesis now declares `petersburgBlock` beside it.

Petersburg's unconditional requirement added exactly one fixture edit — the `core/state_processor_test.go` config that schedules `istanbulBlock` now declares `petersburgBlock`, because the shape upstream rejects is rejected here too. The pair check added none: measured with an overlay prototype across `./core/... ./miner/... ./cmd/XDC/... ./consensus/... ./eth/... ./internal/ethapi/...` (42 packages, zero failures) before it was written, and the one fixture that does declare `constantinopleBlock` without `petersburgBlock` (`core/genesis_setup_test.go`) never reaches the check — its chain ID resolves to the built-in Localnet profile, which backfills `TIPXDCXCancellationFeeBlock` first. The shapes the two rules separate are pinned as tests instead — `petersburg absent without constantinople`, `petersburg skipped while constantinople is declared` and `petersburg skipped with nothing later scheduled` in `TestChainConfigValidateForStartup`'s rejection group, `petersburg declared after constantinople` and `petersburg activated through the cancellation fee fork` in its accepted-prefix group, and `TestChainConfigForkSequencePetersburgPairInvariant` for the pair itself.

### Relation to the `ErrMissingForkSwitch` family and to upstream

The sequence scan is separate from, and runs after, the `ErrMissingForkSwitch` family (`TIPTRC21FeeBlock`, `Gas50xBlock`, the four system-contract addresses). That family is gated by `requiresXDCForkConfig()` (`params/config.go:490-505`), which answers true when any XDC fork block or system-contract field is set or when `XDPoS` is non-nil, because those fields cannot be inferred from Ethereum defaults. The sequence scan must not be gated that way: the hole it closes is reachable from a plain Ethereum-shaped config, which issue #2771 reproduces with nothing but `ChainID`, `OsakaBlock` and `Ethash`. Gating it on `requiresXDCForkConfig()` would leave every pure-Ethereum custom genesis unvalidated, which is the shape that motivated the check in the first place.

Three boundaries against upstream go-ethereum are worth naming. `Osaka` without `Prague` is rejected here and accepted upstream, because `pragueTime` is optional there while every slot here is optional, so upstream's `not enabled, but … enabled` branch cannot fire on the post-Shanghai slots. `PetersburgBlock` missing while a later standard slot is scheduled is rejected on both sides, and for the same reason: upstream's non-optional `petersburgBlock` and `istanbulBlock` entries reject a scheduled `istanbulBlock` when `petersburgBlock` is unset, and this repository reaches the same verdict through the sequence scan. The one shape where this check is stricter is a schedule that stops at `ConstantinopleBlock`: upstream's existence branch needs a later non-optional slot to carry a value, so it never fires there, while `chainConfigForkSequencePetersburgPair` rejects it, because `IsConstantinople` alone then leaves the net-metered EIP-1283 SSTORE rule running with no fork declaring it. `Istanbul` missing is rejected on both sides, since `istanbulBlock` is not optional upstream either. A missing `EIP1559` is not a difference of strictness but a whole extra slot: upstream has no `eip1559Block`, and the rules this repository hangs on that flag (the code and initcode limits, EIP-3541, EIP-3860) sit on upstream's non-optional `berlin`, `london` and `shanghai` entries instead.

## Considered options

- **Flip `forkOrderOptional` for the standard slots and use upstream's semantics.** Rejected: the advance rule here is already `!optional || block != nil`, identical to upstream's `!cur.optional || (cur.block != nil || cur.timestamp != nil)`, so nothing needed changing there; rewriting the advance to `block != nil` would make the existence branch unreachable and turn the new check into a no-op, while not filtering out the trailing XDC forks would add a fourth rejection shape; and the generator emits a nil `optional` predicate for non-optional slots, so `ForEachChainConfigForkOrderBlock` would panic until a predicate was supplied. The data-driven scan reuses the same field descriptors without touching `optional` at all.
- **Require the whole standard sequence, i.e. make all 16 slots required.** Rejected: XDCMainnet, Testnet, Devnet and Localnet intentionally leave `constantinopleBlock`, `petersburgBlock` and `istanbulBlock` empty, so they would be rejected. The data shows this is a design rather than an oversight: `params/config_forks.go:58-81` documents the migrated cancellation-fee fork as the effective Petersburg/Istanbul cutoff for exactly those networks.
- **Count `TIPXDCXMinerDisableBlock` as Istanbul's effective activation.** Rejected: it would make the check accept a config whose `IsIstanbul` never becomes true, the XDCv2 bag only covers the window from the miner disable to EIP1559, and the instruction-set switch does not consult `IsXDCxDisable`. Recorded here so a later reader does not add it as an obvious completion.
- **Honour the `TIPXDCXCancellationFeeBlock` fallback only when the config declares at least one other standard slot.** Rejected: it would let a config rejected today run with `IsIstanbul` true while no Byzantium-era rule is enabled, and it would make the check disagree with `IsIstanbul`, which is exactly the predicate the fallback is keyed on. The migration note above records what that agreement costs an existing pure-XDC config, so it is a known price rather than an oversight.
- **Mark `PetersburgBlock` required unconditionally.** Rejected: it would also reject a config that never declares `ConstantinopleBlock`, where an unset `PetersburgBlock` is correct — `IsConstantinople` is false, so `IsPetersburg || !IsConstantinople` takes the legacy branch, and upstream's `IsPetersburg` agrees. Measured on 2026-10-09: that variant rejects `{Homestead..Byzantium, IstanbulBlock, BerlinBlock}` with `PetersburgBlock is unset, but IstanbulBlock 0 is scheduled`, a shape upstream accepts, while the conditional form accepts it and still rejects `{ConstantinopleBlock, IstanbulBlock}` with an unset `PetersburgBlock`. **Superseded on 2026-10-10:** the rejection rested on "a shape upstream accepts", and that premise is false. Measured against geth master `93d4038b0`, upstream rejects the same config with `petersburgBlock not enabled, but istanbulBlock enabled at block 0`, because `petersburgBlock` and `istanbulBlock` are non-optional there; geth #21473 states the intent directly. The unconditional requirement is taken as of this revision, and the Petersburg paragraph in `## Decision` records the current rationale.

## Out of scope

- The size-limit, EIP-3541 and empty-account symptoms listed in issue #2771 are closed indirectly rather than repaired: the flags they key on (`IsEIP158` for `CheckMaxCodeSize`, the empty-account deletion rule and `IsEIP1559` for `CheckMaxInitCodeSize`, EIP-3541 in `core/vm/evm.go`) are all in the required set, so a config that would run without them no longer starts. Making a *consistent* early schedule use the later caps, or deriving the caps from the highest configured fork, stays a separate decision (the Osaka-tier cap arrived with #2757).
- The one-way shape above (complete prefix, later forks absent) and its EIP-3860 consequence.
- The linear fork comparison (`params/config.go`) still compares the raw `IstanbulBlock`/`PetersburgBlock` fields against `TIPXDCXCancellationFeeBlock` as if the three were independent forks, so a config that declares an explicit slot and sets the fallback earlier is rejected with `IstanbulBlock 100 > TIPXDCXCancellationFeeBlock 0` even though `IsIstanbul`/`IsPetersburg` OR the two and activate at the earlier value. Reproduced on the baseline (`22a40a58f`) as well, so it predates this check; the sequence scan neither introduces nor repairs it.
- `XDPoS.NewFaker`'s contract (`consensus/XDPoS/XDPoS.go:141`): it validates and returns a bare nil on failure, which is why a rejected fixture panics at the call site instead of reporting the error. Unchanged here; its call sites are tracked separately.
