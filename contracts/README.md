# contracts

Solidity sources and checked-in `abigen` bindings of the built-in system
contracts, plus a few fixtures. The sources here are a historical record of what
was deployed, not the recommended way to write or build contracts today.

## Historical system contract sources

These contracts are already deployed on mainnet and Apothem. Their addresses come
either from the constants in `common/types.go` (for example the validator voting
contract at `0x…0088`, the block signer at `0x…0089`, the randomize contract at
`0x…0090`) or from each network's `ChainConfig` in `params/config_networks.go`
(for example `XDCXListingSMC`). The code running at those addresses is shipped in
the genesis allocations (`core/genesis_alloc_mainnet.go`,
`core/genesis_alloc_testnet.go`, `core/genesis_alloc_devnet.go`), not compiled
from these sources, which are kept to document what was deployed:

| Source | Contract | pragma |
| --- | --- | --- |
| `validator/contract/XDCValidator.sol` | XDCValidator | `^0.4.21` |
| `blocksigner/contract/BlockSigner.sol` | BlockSigner | `^0.4.21` |
| `randomize/contract/XDCRandomize.sol` | XDCRandomize | `^0.4.21` |
| `multisigwallet/contract/MultiSigWallet.sol` | MultiSigWallet | `^0.4.21` |
| `trc21issuer/contract/TRC21.sol`, `TRC21Issuer.sol` | TRC21, TRC21Issuer | `^0.4.24` |
| `XDCx/contract/*.sol` | Registration, LendingRegistration, XDCXListing, … | `0.4.24` / `^0.4.24` |

The `libs/SafeMath.sol` files beside them belong to the same deployments and are
pinned to the same compiler versions.

Do not modernise them. Raising the pragma or recompiling with a current `solc`
changes the metadata hash and therefore the bytecode, which then no longer
matches what those addresses hold on chain. Nothing in the build compiles these
files; `Makefile` mentions `solc` only in its `devtools` target.

## Bindings

The `*.go` files in the same directories are generated bindings, carrying both the
ABI and the `…Bin` bytecode. The node uses the ABI at runtime
(`contracts/validator`, `contracts/blocksigner`, `internal/ethapi`), and the
bytecode is used to deploy fresh copies of the contracts in the engine tests
(`consensus/tests/engine_v1_tests`, `consensus/tests/engine_v2_tests`). They are
generated by the in-tree `cmd/abigen`, so regenerate them when the deployed
contract itself changes, or when the abigen template changes underneath them.

Each binding file is regenerated from a committed combined-json input next to the
sources (`<binding>.json`, for example `validator/contract/validator.json`), which
carries the ABI and the deployment bytecode of every type in that binding. The
`//go:generate` directives live in the `generate.go` file of each `contract/`
directory; `make generate` re-runs them and fails if any tracked file changes, so
template drift below these files is caught by CI.

The inputs were reconstructed once and verified against the sources: the ABI in
each json compiles byte-identically (as a set) from the `.sol` files with the
compiler versions below, and for every type except the two noted under "Known
divergence" the code part of the bytecode (everything before the trailing
metadata hash) is byte-identical too. The `bin` field keeps the committed
bytecode rather than a fresh compile: the 0.4.x/0.6.x metadata hash embeds
compile-time details (exact source text as compiled, build settings) that cannot
be reproduced today, so a fresh compile never matches byte-for-byte.

| Binding | Reproduced with |
| --- | --- |
| `blocksigner/contract/blocksigner.go` | solc 0.4.21 `--optimize` |
| `multisigwallet/contract/multisigwallet.go` | solc 0.4.21 `--optimize` |
| `randomize/contract/randomize.go` | solc 0.4.21 `--optimize` |
| `validator/contract/validator.go` | solc 0.4.21 (no optimizer) |
| `trc21issuer/contract/TRC21.go`, `TRC21Issuer.go` | solc 0.4.24 `--optimize` |
| `XDCx/contract/TRC21.go`, `TRC21Issuer.go`, `XDCXListing.go` | solc 0.4.24 `--optimize` |
| `tests/contract/Inherited.go` | solc 0.6.10 `--optimize` |

The 0.4.x binaries are EOL and nothing in the build installs them; the table
records provenance, it does not make them a build dependency. Editing a `.sol`
below these bindings does not fail `make generate` (that guard pins the generated
output, not the sources) — recompile by hand, compare, and refresh both the json
and the binding together.

### Known divergence

The committed bytecode of `RelayerRegistration` (`XDCx/contract/Registration.go`)
and `Lending` (`XDCx/contract/LendingRegistration.go`) was compiled from
pre-rebrand TomoChain sources that never entered this repository: the binaries
carry TOMO-era `require` messages where the committed sources say XDC, and
`Lending`'s runtime code differs beyond that. Their ABIs still match the current
sources exactly. The bytecode is kept as committed — it is what the fork
historically shipped — until the trade-off in #2886 is decided; regenerating
these two bindings from their json inputs reproduces them byte-for-byte, so the
guard is not affected.

## Other Solidity here

- `solidity_0.6/` holds small samples of the syntax changes introduced by
  Solidity 0.6; its own `README.md` describes them. Illustrations, not templates.
- `tests/contract/` holds the `Inherited` fixture used by `contracts/tests`. Not a
  system contract.

## Writing new contracts

For anything new, follow `docs/solidity.md`: use a current 0.8.x compiler and pin
`evmVersion` explicitly to the fork your target network has activated.
